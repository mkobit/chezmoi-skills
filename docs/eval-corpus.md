# Adding evaluation cases to the corpus

Evaluation cases live as JSON arrays under `tests/evals/*_eval.json`, with one file per skill.

`loadCorpus` in [corpus.ts](../scripts/evals/corpus.ts) reads every `.json` file in `tests/evals/` and parses it against `TestCaseSchema`.

## Corpus layout and file naming

Add new cases to the matching skill file under `tests/evals/`:

| Skill | Corpus file | Skill code |

| `chezmoi-cli-commands` | [cli_commands_eval.json](../tests/evals/cli_commands_eval.json) | `CLI` |

## Case ID conventions

Use unique, zero-padded IDs following `TC-<SKILL_CODE>-<TYPE>-<NNN>` (for example, `TC-CLI-CMD-001`).

Common `<TYPE>` segments in the corpus are:

* `TRIG`: Trigger matching cases (`should_trigger: true` or `false`).
* `SEL`: Skill selection cases.
* `CMD`: Command correctness cases.
* `ANS` or `QUAL`: Answer quality cases.
* `SAFETY`: Safety or confirmation-first cases.
* `ADV` or `AMB`: Adversarial or ambiguous routing cases.
* `SYN`: Synthetic candidates generated by `bun run eval:live:generate`.

## TestCaseSchema fields

Every element in a `*_eval.json` array must satisfy `TestCaseSchema` in [corpus.ts](../scripts/evals/corpus.ts).

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `id` | `string` | Yes | Unique case identifier across the corpus. |
| `name` | `string` | Yes | Short description of what the case verifies. |
| `eval_type` | `enum` | Yes | One of `trigger_matching`, `skill_selection`, `command_correctness`, or `answer_quality`. |
| `target_skill` | `string` | Yes | Skill `name` matching frontmatter in `skills/<skill>/SKILL.md`. |
| `origin` | `enum` | No | Provenance: `contrived` (default), `distilled`, or `synthetic`. |
| `smoke` | `boolean` | No | Set `true` to include the case in `bun run eval:live --smoke`. |
| `input` | `object` | Yes | Prompt and optional workspace context files. |
| `expected` | `object` | Yes | Deterministic assertions and optional judge rubric. |
| `token_budget` | `number` | No | Optional token budget metadata for the case. |
| `mock_responses` | `array` | No | Per-case `chezmoi` shim responses. |
| `simulation` | `object` | No | Multi-turn user simulator settings. |

### Input fields

* `user_prompt` (`string`, required): The prompt sent to the agent.
* `context_files` (`string[]`, optional): Relative paths under `skills/` materialized into the isolated case workspace and checked for existence by `validate:contracts`.

### Origin and smoke fields

* Set `origin` to `contrived` (or omit it) for hand-authored cases, `distilled` for cases extracted from real agent transcripts, and `synthetic` for cases produced by the synthetic generator.
* Filter runs by provenance with `bun run eval:live --origin <contrived|distilled|synthetic>`.
* Keep `smoke: true` limited to a fast representative subset across skills so `bun run eval:live --smoke` remains practical after edits.

### Expected assertion fields

Assertion fields inside `expected` depend on `eval_type`:

* **`trigger_matching`**:
  * `should_trigger` (`boolean`, required): `true` requires `target_skill` in `discovered_skills`; `false` requires an empty `discovered_skills` list.
  * `validate:contracts` requires `user_prompt` to contain a `chezmoi` or `dotfile(s)` cue when `should_trigger` is `true`, and to omit those cues when `should_trigger` is `false`.
* **`skill_selection`**:
  * `selected_skill` (`string`, optional) or `selected_skills` (`string[]`, min 1, optional): Allowed discovered skill names; defaults to `[target_skill]`.
  * `allow_clarification` (`boolean`, optional): When `true`, a `final_response` containing `?` also satisfies routing.
  * `validate:contracts` requires at least one non-generic token from `user_prompt` to appear in the target skill's markdown files.
* **`command_correctness`**:
  * `exact_command` (`string`, optional): Candidate command must equal or include this string.
  * `command_regex` (`string`, optional): Candidate command must match this regular expression.
  * `required_flags` (`string[]`, optional): Every listed flag must appear in the matched candidate.
  * `forbidden_flags` (`string[]`, optional): None of the listed flags may appear in the matched candidate.
  * `allow_prose_command` (`boolean`, optional): When `true`, also extract inline code and lines from `final_response` instead of checking only invoked commands.
  * `validate:contracts` requires derived command and `required_flags` terms to appear in the target skill's markdown files.
* **`answer_quality`**:
  * `answer_quality` (`object`, required): Must include at least one of `required_concepts` (`string[]`), `forbidden_claims` (`string[]`), `safety_expectations` (`string[]`), or `clarification` (`"required" | "forbidden"`).
  * Concept, claim, and safety checks match case-insensitive substrings against `final_response`; `clarification` checks for `?`.

Two `expected` fields apply across any `eval_type`:

* `required_references` (`string[]`, optional): Skill reference paths (such as `references/diff.md`) that must appear in `references_read`.
* `rubric` (`object`, optional): LLM-as-judge criteria (`criteria` of 1..8 `{ id, description, critical? }` objects with `critical` defaulting to `true`, `min_pass_ratio` in `0..1` defaulting to `1`, and optional `include_references`).

### Mock responses and simulation

* Each `mock_responses` entry requires at least one of `match_args` (`string[]`) or `match_regex` (`string`), plus optional `stdout`, `stderr`, and `exit_code` (`0..255`).
* A `simulation` object configures multi-turn runs with `persona`, `goal`, non-empty `scenario_facts` (`string[]`), `max_turns` (`2..8`, default `4`), and `shim_call_cap` (`1..40`, default `25`).

## Promoting synthetic and transcript candidates

Never write generated or extracted cases directly into `tests/evals/` without review.

### Synthetic candidates

Generate candidate edge cases into gitignored staging under `eval_results/generated/<timestamp>-<skill>/`:

```sh
bun run eval:live:generate --skill chezmoi-cli-commands --focus flag_edge_case --count 5
```

1. Inspect `cases.json` and `report.md` in the staging directory.
2. Candidates have already passed the generator's `schema`, `security_lint`, `deduplication`, and `contract` gates and carry `origin: "synthetic"` with `TC-<SKILL_CODE>-SYN-<NNN>` IDs.
3. Copy approved cases into the target `tests/evals/*_eval.json` array, verify unique IDs and `smoke` tags, and validate.

### Review a sampled Codex session

Run `scripts/review-chezmoi-session.py` from the dotfiles checkout to accept a personal session and open a Codex fork in this repo.
Set `CHEZMOI_SKILLS_CHECKOUT` to the path of this checkout if it is outside your usual workspace.
The [session review skill](../.agents/skills/session-eval-review/SKILL.md) stages one redacted candidate under `eval_results/session-review/`.
Check that the case has an observable expected result and contains only the context needed to reproduce it.
Promote approved cases to the matching corpus file, then run the validation steps below.
See the [capture design](designs/session-eval-capture.md) for the opt-in and sampling workflow.

### Transcript candidates

Extract candidate cases from agent transcript JSONL logs using [extract-transcript-evals.ts](../scripts/evals/extract-transcript-evals.ts):

```sh
# Preview extracted cases without writing files
bun run extract:evals --input <transcript-or-dir> --target-skill chezmoi-cli-commands --id-prefix TC-CLI-DIST --dry-run

# Stage extracted cases outside tests/evals/ for review
bun run extract:evals --input <transcript-or-dir> --target-skill chezmoi-cli-commands --id-prefix TC-CLI-DIST --out-dir eval_results/extracted
```

1. Pass `--out-dir` outside `tests/evals/` (the CLI defaults `--out-dir` to `tests/evals` and writes `extracted_evals.json`).
2. Review every extracted case (`origin: "distilled"`), strip any remaining environment-specific details, refine `expected` assertions, and rename IDs to match corpus conventions before moving approved entries into `tests/evals/*_eval.json`.

## Validating corpus changes

Run offline schema, contract, test, and lint checks after every corpus edit:

```sh
bun run validate:evals
bun run validate:contracts
bun test
mise run lint
```

* `bun run validate:evals` validates every `tests/evals/*.json` file against `TestCaseSchema` and validates `tests/evals/history.jsonl` if present.
* `bun run validate:contracts` checks that each case's `target_skill`, `context_files`, trigger cues, prompt overlap, command coverage, and `answer_quality` expectations align with `skills/`.
* Run `bun run eval:live --case <NEW_CASE_ID>` (or `--smoke`) locally when you want live harness verification before opening a pull request.
